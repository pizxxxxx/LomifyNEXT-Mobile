# Общие релизы Android и iOS

Начиная с 1.0.29, публикуется одна общая страница с двумя файлами.
С 1.0.31 используется технический тег `ios-v<версия>`: он нужен кнопке
обновления в уже установленных старых iOS-приложениях. Название страницы
остаётся `LomifyNEXT Mobile <версия> — Android и iOS`; это общий релиз,
а не отдельный выпуск для iPhone.

- `LomifyNEXT-<версия>-arm64.apk` — Android, подпись прежним Windows-ключом.
- `LomifyNEXT-<версия>.ipa` — iPhone, device ARM64 без персональной подписи;
  установка и подпись через AltStore Classic.

Описание включает изменения и установку обеих платформ. Контрольные суммы
обоих файлов находятся в `SHA256SUMS.txt`. Исходники Android публикуются
в `main`, iOS — в `ios`; перед общей сборкой синхронизируются общие изменения.
Платформенные части остаются защищены `cfg` и проверками платформы в UI.

## Совместимость кнопок обновления

Android выбирает версию по имени APK. iOS начиная с 1.0.29 выбирает версию по имени
IPA; для этого кода префикс тега не имеет значения. Проверяются
адреса именно этого репозитория, черновики и отсутствие нужного файла.
APK не подменяет iOS-обновление, IPA не подменяет Android-обновление.

Кнопка обновления в iOS 1.0.25–1.0.27 ищет только теги `ios-v`. Общие выпуски
1.0.29 и 1.0.30 с тегами `v<версия>` этим кодом пропускались: кнопка продолжала
открывать 1.0.27. В 1.0.31 общий тег снова совместим со старым кодом, поэтому
кнопка в установленной 1.0.27 открывает новый релиз напрямую. Android видит
APK на той же странице независимо от префикса.

Старые отдельные и общие релизы и их assets остаются историей:
скачивание по существующим ссылкам не ломается.

## Перед публикацией

1. Увеличить общую версию и номера сборок через `npm run version:next`.
2. Собрать обе платформы с пустым каталогом переменных окружения агента.
3. Подписать Android прежним ключом вне Git, проверить сертификат,
   выравнивание и versionCode. IPA проверить по версии и архитектуре.
4. Показать git status и diff перед коммитом, загрузить `main` и `ios`.
5. Создать один тег `ios-v<версия>` и один релиз с обоими файлами, контрольными суммами
   и описанием из `docs/releases/v<версия>.md`.
6. Сверить хэши загруженных assets с локальными файлами. Проверить ответы
   публичного GitHub API без авторизации: старый iOS 1.0.27, новый iOS и Android
   должны выбрать этот общий релиз и файл своей платформы. Он должен быть Latest.

Регрессионная проверка: `node scripts/mobile-updates-test.mjs`. Она запускает
и текущий код, и неизменённый снимок `mobileUpdateCore.ts` из выпущенной iOS
1.0.27 (коммит `de91a280`). Пока поддерживаются обновления с iOS 1.0.25–1.0.27,
последующие общие выпуски сохраняют префикс `ios-v`.

AltStore source не создаётся; iOS обновляется ручным выбором новой IPA.
